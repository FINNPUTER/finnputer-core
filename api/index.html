API

Read the buyers,
from your own code.

The same engine behind the scanner, over HTTP. Wallet scores across five chains, cluster and funding detection, and the full record of what we published. JSON, no SDK, no signup to try it.

BASE URL

https://api.finnputerdex.com

Every response is JSON. CORS is open, so a browser can call it directly. No key is needed to start: unkeyed callers share a daily allowance, which is enough to try everything here and not enough to run a product on.

THE ONE THAT MATTERS

Everything else is a lookup. This is the call that does the work: it reads the token, the holders, the clusters and the funding relationships between the early buyers, and tells you which of them have a record with us.

curl -X POST https://api.finnputerdex.com/v1/scan \
  -H "content-type: application/json" \
  -d '{"mint":"E3HSQRoXC34RVPWYYDuxm4cNBspwBaVRSqBnRdEFpump","depth":"deep"}'

A deep scan takes up to 90 seconds the first time and is cached for 15 minutes. Pass "fresh": true to skip the cache. The chain is worked out by asking which one actually trades the address, so you do not have to know it.

A check we could not run comes back as unmeasured, never as a pass. That distinction is the whole point: an absent measurement and a clean result are different answers, and most scanners return the same thing for both.

ENDPOINTS

POST
/v1/scan
Full analysis of one token. Body: mint, depth (quick or deep), optional chain, optional fresh.
GET
/v1/scan/cached
The cached report only, or cached:false. Never starts a scan, so it is safe to call per row on a page.
GET
/v1/wallet/{address}
One wallet: score, label, how many tokens it was early in that later ran, and what we have seen it close.
GET
/v1/smart-money
The wallet ranking. Bundlers, handed positions and infrastructure are labelled and never ranked.
GET
/v1/token/{mint}/smart-money
Which rated wallets bought this token, with size and timestamp. The agent question: is anyone good in here.
GET
/v1/opportunities
Live convergence: several independent rated wallets buying the same token inside one window.
GET
/v1/runners
Tokens we witnessed run, with entry and peak.
GET
/v1/signals
What we published, newest first, with a cursor. kind is solo (one rated wallet), signal (several agreeing) or scan (passed the bar with no rated wallet behind it). peak_multiple is null until the follow-up has re-checked it, never 0.
GET
/v1/track-record
What we published and what it did. The same figures the site shows, including the ones that went nowhere.
GET
/v1/buys
Recent buys by rated wallets. Add /tokens for the same data grouped by token.
GET
/v1/resolve
Which chain actually trades an address.
GET
/v1/stats
How many wallets are scored, how many tokens scanned. Useful as a health check.

KEYS AND LIMITS

Send a key as x-api-key when you need more than the shared allowance. A deep scan costs more than a lookup because it costs us more: a cached one is charged at a tenth.

curl https://api.finnputerdex.com/v1/smart-money \
  -H "x-api-key: YOUR_KEY"

For a key, or for a volume that does not fit the standard allowance, write to partners@finnputerdex.com.

REACTING TO SIGNALS WHILE YOU ARE AWAY

Two feeds, and which one you want depends on how early you need to be. /v1/signals is what we published, the same thing the channel gets and at the same moment: after the 10 minute head start holders have. With a holder key in X-Api-Key it is live. /v1/buys is a step earlier: every rated wallet buy we see, including the ones that never become a signal.

Both take a cursor. The response carries cursor, the timestamp of the newest row in it. Pass it back as since on the next call and nothing arrives twice, so a loop on a VPS needs no memory of its own.

cursor=0
while true; do
  r=$(curl -s "https://api.finnputerdex.com/v1/signals?since=$cursor")
  echo "$r" | jq -c '.signals[]'       # act on each new signal
  cursor=$(echo "$r" | jq -r '.cursor')
  sleep 30
done

chain and kind narrow it further.

Swap /v1/signals for /v1/buys?min=50 to work from the raw wallet buys instead. There you also want min, the wallet score floor: without it you are reading every rated buy rather than the ones with a record behind them.

Thirty seconds is a reasonable loop. Faster costs you allowance and buys little: the alert and the chain are the slow parts, not the poll.

Push, rather than polling, is the better answer and does not exist yet. If you want a webhook, say so and say what shape you need it in. We would rather build the one that fits a real integration than guess at it.

FOR AGENTS

The endpoints are plain HTTP GET and POST with JSON bodies, which is what a tool-calling agent wants: no SDK, no session, no signing. A machine-payable endpoint is available at api.finnputerdex.com for callers that settle per request rather than holding a key.

If you are wiring this into an agent and something in the shape of a response makes that harder than it should be, say so. We would rather change it than have you work around it.

IN CLAUDE, AS A CONNECTOR

The same data is an MCP server. Add it once and ask Claude things like "is this token bundled?" or "what did FINNPUTER publish today?", and the answer comes from these numbers.

https://mcp.finnputerdex.com/mcp

In Claude: Connectors, the plus button, then a name and this URL. Opened in a browser it answers "405 Method Not Allowed", which is correct: MCP clients talk to it by POST. No key, no login. Four tools, all read only: scan_token, recent_signals, wallet_score and track_record.

Holders of $50 of $FINNPUTER get a free key in the bot, under 🔑 Claude key. Add it in the connector as a request header named X-Api-Key: signals then arrive live instead of after the head start, with your own deep scans each day.

A scan through the connector returns the quick scan plus the latest deep scan anyone already ran. New deep scans are shared across all connector users and limited per day, because each one reads a token's whole launch history. Nothing here can trade or move funds.

WHAT THIS IS NOT

Read only. Nothing here moves funds, holds funds or executes a trade. Nothing on this page is financial advice, an offer or a recommendation. Figures come from public chain data and third party price sources and can be wrong, incomplete or out of date.
